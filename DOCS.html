Nano Fabricator Code Guide

CCC Linz Oct 2026, levels 1–6. Code: ccc/contest.py, ccc/__main__.py (load), ccc/run.py, ccc/contest_test.py. See also: animations, level 6 strategy explorer.

1The problem in 6 lines

L1
Draw an empty hexagon board of radius r: O cells, * border, - padding only.
L2
One emitter digit 1–6 on the border fires a straight beam; every O it crosses becomes matter M.
L3
Up to 6 emitters fire at once. A cell hit by 2 beams becomes M, 3+ beams destroy it (O), 0–1 leave it as is. Beams pass O/M and stop at * or a digit.
L4
Input is a program, not a board. Six emitters start inactive on the corners. Each tick, all 6 commands apply at once (F/B move one border cell clockwise/counter-clockwise, T toggles on/off, - does nothing), then the active ones fire with the L3 rule.
L5
Each item is a pattern board plus an L4 program. After each tick, the pattern is submitted when all its M cells are M and no other M touches them; its cells go back to O and the count goes up. Output: one count per line.
L6
Inverse of L5: given a pattern and a count k, write the program. Valid if it submits ≥ k times; score = total lines. See section 7.

L1 is not in RULES and its input (bare radii) does not go through load; hexagon(r) produces it directly.

3Board representation

Board = dict[Cell, str] with Cell = (row, col), the character's position in the ASCII rows. The - gaps are left out, so every key is a real cell (O, M, * or a digit). Neighbours sit 2 columns apart in a row and 1 column apart diagonally: “doubled-width” coordinates.

hexagon(2)           keys (row, col)                        ring(2) index
--*-*-*--                  (0,2) (0,4) (0,6)                    2  3  4
-*-O-O-*-               (1,1) (1,3) (1,5) (1,7)               1  .  .  5
*-O-O-O-*            (2,0) (2,2) (2,4) (2,6) (2,8)          0  .  .  .  6
-*-O-O-*-               (3,1) (3,3) (3,5) (3,7)              11  .  .  7
--*-*-*--                  (4,2) (4,4) (4,6)                   10  9  8

DIRS: emitter digit → (row, col) step, clockwise starting east.

digit123456
arrow→↘↙←↖↗
step(0,2)(1,1)(1,-1)(0,-2)(-1,-1)(-1,1)

Why this over the alternatives:

  • Raw grid (list of strings): immutable rows, the - gaps sit between cells, and every step needs a bounds check. The dict has none of that: b.get(cell) is None off the board, so ray just stops.
  • Axial (q, r): nicer maths, but parse/render would need a conversion. Here they are one-liners and a key is exactly where the character prints.
  • numpy: boards are small and the work is walking rays cell by cell, so there is nothing to vectorise, and the gaps would still be in the array.

Rule: only parse, render, DIRS, ray, neighbours, hexagon and ring touch raw coordinates. Everything else treats cells as opaque keys (cell in board, a Counter), so switching to axial would only change those seven.

5Adding a new level

  • Write a new rule item -> Board or item -> int (fireN, runN, ...) from the building blocks; split a block out of an old rule if needed. Leave old rules unchanged so old levels stay solvable.
  • Add it to RULES = {level: rule} at the bottom of contest.py. solve defaults to max(RULES).
  • If the input format changes, add a branch to load in ccc/__main__.py (it dispatches on the number of tokens in the item header and on what follows the board rows; read_ticks reads a tick block).
  • uv run python -m ccc.run [N] [filter] (level defaults to max(RULES)) always checks the example first against out_level-N_0-example.txt (exits on mismatch), then writes out_level-N_*.txt for the real inputs in name order, printing each file's time. filter keeps only inputs whose name contains it, e.g. python -m ccc.run 5 small.
  • test_outputs picks up every out_level-N_*.txt for levels in RULES automatically. Add a small hand-traced test on hexagon(2) (the small() helper), and add the level to BOARD_LEVELS if its items are boards.

7Level 6: strategies and results

Status: the portfolio program6 is valid on every file. Large and enormous are still being computed, and no score has been confirmed by an upload yet. Interactive versions of the sketches below: STRATEGIES.html; L4/L5 mechanics: ANIMATIONS.html.

Problem. Each item is a pattern plus a required count k. Output a tick program (F/B/T/- per emitter, L4 format) that submits the pattern at least k times under the L5 rules. Score = total program lines, lower is better.

7.1 Judge facts

Read from the contest sandbox's JS, then checked with a Python port (review6/judge.py) and by fuzzing 3000 programs: 0 mismatches.

  • It accepts ≥ k submissions, and at most 1 submission per tick.
  • Every line is a tick, all-- lines included.
  • Detection is at a fixed position. The halo (in-board O cells next to the pattern) must not be M. Every other cell is don't-care.
  • The board persists within a program. Beams skip non-O/M cells, which matches our ray.

valid6 requires exactly k submissions, which is stricter than the judge. try_cycles cuts every program right after the k-th submission, so this never costs lines.

  • Arc. Emitter k is only useful at offsets −(r−1)..r−1 around its home corner k·r, and each such position fires one full chord (chords(r): int bitsets). At ±r it would sit on the next corner and shine along the border.
  • Movement is cheap. Moves on the arc never wrap, so the cost is |Δo|. Emitters move in parallel and can pre-position while off. One beam alone is harmless (1 hit). Lower bound for one transition: max over emitters of (ring distance + toggle).
  • Opposite pairs. Pairs 1/4, 2/5 and 3/6 at negated offsets lie on the same chord, so turning both on builds that whole line.
  • Hit counting. count_hits is a bitwise adder over the beam masks. It returns the cells hit exactly 2× (become M) and 3+× (cleared). zone6 gives the pattern and halo masks. The halo is built from a set, because summing double-counted cells (a real bug).

7.3 The key insight: every repetition is the same problem

After a submission, the pattern cells go back to O, and the halo had to be O for the submission to count. So the zone that matters is blank again, and every repetition is identical. A strategy is therefore a cycle of m fire configs (an offset or off per emitter), repeated k times:

lines = setup + 1 + (k·m − 1)·gap         cycle_lines()
        setup = walk from home to the first config   cycle_setup()
        gap   = ticks between fires (1 if moves fit)  cycle_gap()
lower bound: lines ≥ k·m*, m* = fewest fire ticks one build needs

So m matters most, then gap, and setup is paid once. cycle_program turns a cycle into ticks: off emitters walk early and toggle on at their fire, while emitters used in consecutive fires stay on and move just before the next one. try_cycles simulates the 30 most promising cycles in every rotation with submissions6 (run5 on bitmasks) and keeps the shortest.

Shared search space: effects6 brute-forces every config over the chords that touch the zone and groups them by effect (2-hit cells, 3+-hit cells), keeping the KEEP=40 cheapest per effect. Every search step stops after BUDGET = 3 s per item.

7.4 Baseline: driver pair + greedy helpers done

idea
Two driver emitters BFS (drive) to a state where their beams cross on an unbuilt pattern cell, and never cross on the halo on the way. Each tick, the other 4 pick the best of their ≤ 44 command combinations: score 1000 per newly built cell, plus how close each one is to a chord rich in unbuilt cells. A combination is rejected if it puts 2 hits on a halo cell or 3+ on a built cell. baseline6 takes the best of the 6 driver PAIRS.
cost
No formula. Navigation for every cell, rebuilt from scratch for every repetition.
wins
Always valid on any pattern, so it is the fallback in program6. Fine when k is 1–2.
fails
It never reuses a configuration, so cost grows with k, which hurts on medium (Σk = 2045).

7.5 Single-tick frame (frame6, m = 1) done

idea
Find one config whose 2-hit cells in the zone are exactly the pattern. Walk there, toggle on, and leave it on: every tick re-fires it, rebuilds the pattern from blank and submits again.
sketch
tick       1  2  3  4  5      (k = 3, farthest offset 2)
emitter a  F  F  T  -  -
emitter b  B  -  T  -  -
emitter c  -  -  T  -  -
submit           #1 #2 #3
cost
setup + k, which matches the lower bound up to the setup.
wins
Patterns that are crossing points of ≤ 6 chords and/or full lines from opposite pairs.
fails
Almost everything else. 6 chords cross in ≤ 15 points (MAX_BUILT), and real patterns are single blobs. A frame exists for only 4/10 small, 9/210 medium, 1/190 large and 0/140 enormous items.

7.6 Two-tick A/B cycle (pair6, m = 2) done

idea
Fire A, then B. B (a "last" effect) builds part of the pattern and destroys none of it. A builds the rest and may leave stray halo M, which B's 3+ hits clear. Only the state after B has to be clean. Emitters on in both fires slide between them, and the others toggle.
sketch
tick      s  A  B  A  B  A  B
shared    .  F  B  F  B  F  B     on in both: move 1 per tick (gap 1)
A-only    .  T  T  T  T  T  T     on for A, off for B
submit          #1    #2    #3
cost
setup + 1 + (2k−1)·gap, about 2k when gap = 1.
wins
Patterns up to ~30 cells that split into two chord arrangements. This is the workhorse on medium.
fails
When the halo gets in the way (A would need a stray M that B can't clear), or when the shared emitters must move far (gap > 1 doubles the cost).

7.7 Three-tick cycles (triple6, cover6, m = 3) done

idea
triple6: A, B, C, where C is a "last" effect. After C, exactly the pattern stands, and C's 3+ hits clear what A and B left in the halo. Neither A alone nor A+B may complete the pattern. cover6 is the narrow, quick case: B and C are two big, clean, nondestructive frames and A fills the rest, so every tick only adds cells.
cost
setup + 1 + (3k−1)·gap.
wins
Mid-size blobs (up to 45 cells) where no pair works.
fails
The search space is effect3, so it is cut to the top 40/300 effects and the budget. Big patterns (large, enormous) need more than 3 frames.

7.8 Parked toggle cycle (toggle6) done

idea
Walk up to 6 emitters once to fixed lines (parkings: every pattern cell must lie on ≥ 2 of them). After that, each tick only toggles which of them are on. A BFS over the zone state (toggle_cycle) finds the shortest on-subset sequence that leaves exactly the pattern.
cost
setup + m·k, with gap always 1 because no emitter moves after setup.
wins
Small patterns whose cycle needs long moves between fires. Parking removes all the moving.
fails
Patterns larger than 15 cells, and patterns that no single set of 6 lines covers twice.

7.9 Portfolio (program6) done

It runs baseline6 and then STRATEGIES = [frame6, pair6, triple6, cover6, toggle6], and returns the shortest valid6-checked candidate. It stops early once the baseline is ≤ k+1 lines, because no cycle can beat that. merge6.py keeps the shortest valid program per item across all candidate folders, including remote runs, so the uploaded set only ever improves.

7.11 The settled pipeline running

The portfolio above only seeds the search now. The uploaded programs come from a remote loop of one constructor and two polishers, joined by a per-item merge. Every stage keeps the current best program unless it finds a strictly shorter valid one, so the best set only ever shrinks.

  Rust beam  ──►  exact chain (CP-SAT)  ──►  windowed LNS (CP-SAT)
  (builds)        (rebuilds per copy)        (shaves 2–11 lines)
       ▲                                          │
       └──── best6  ◄── merge6 (valid6) ◄── pull (both boxes)
stagewhat it does
Rust beam
constructor, l6_rust
  • State: 6 emitter offsets plus on flags, the matter on the zone cells (pattern + halo) as u64 bitsets, and the submissions done.
  • Expand: every state tries all 46 = 4096 tick commands, at about 100M combos/s/thread.
  • Score: subs·106 + built − wd·stray_halo_M + potential. The potential rewards emitters near chords that are rich in unbuilt cells (wp, discounted by distance lam), line fills (wl, minus wlh per halo cell on the line), and being on (won), minus eps per action.
  • Runs per item: a "big" preset (wd = 1000, all 4096 children kept per parent) and a default preset at each width, then random weight restarts with new seeds until the time budget runs out. Widths 1600/6400 and 3000/12000, 200–400 s per item.
Exact chain
polisher, l6_ilp		A time-expanded CP-SAT model of the L5 rules on the zone cells only. Each copy after the first is re-solved as the shortest rebuild from the emitter state the previous copy left, which works because the zone is clean after every submission. The same model gives the lower bound Tfirst* + (k−1)·Pmin*.
Windowed LNS
polisher, l6_cpsat		It takes a best program and re-solves sliding windows of 16 and 24 ticks with CP-SAT, hinted from the current program. Each window starts from the exact (emitter states, zone matter) at its first tick and must end in the same state at a variable tick, so a shorter window splices straight in. About 120 s per item pays off; 30 s does not.
merge6 + harvest
local		A pull step copies every ~/scratch/l6_*/out from both boxes. merge6.py keeps the shortest valid6 program per item, with best6 always a candidate. The new best6 goes back to both boxes, and looping runs start their next pass from it.

Who runs what. There are two 32-core EC2 boxes. ccc1 runs the Rust beam on the worst large and enormous items, the CP-SAT LNS, and the chain runners. ccc2 runs a Rust loop over the 60 longest items (new seeds every pass), a run on the large items ranked 60–100, and an experimental beam with a chord-fill bonus. The local machine only harvests, merges and validates.

Why Rust. The tooling study measured the Rust simulator at 37× Python and the combo evaluation at 150–190×. The search is compute-bound (W 25 → 1600 gave −15% lines on a sample), so speed is score.
